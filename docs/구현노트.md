# 구현 노트 — 실제로 부딪힌 함정들

문서 변환기를 만들면서 **실측으로 확인한** 문제와 해결책을 정리했다. 대부분
문서에 잘 안 나오거나, 이름만 보고 넘겨짚으면 틀리는 것들이다. 비슷한 걸 만드는
사람에게 시간을 아껴 주려고 남긴다.

---

## PDF

### 한글 PDF가 26MB가 되는 이유

PDF는 글꼴을 임베딩할 때 **글꼴 파일을 통째로** 넣는다. 라틴 글꼴은 100KB 남짓이라
신경 쓸 일이 없지만, 한중일 글꼴은 글리프가 2만 자를 넘어 파일 자체가 10MB를 넘는다.

```
맑은 고딕 Regular : 13.4 MB
맑은 고딕 Bold    : 12.6 MB
────────────────────────────
결과 PDF          : 26.4 MB   (원본 문서는 32KB)
```

해결은 **서브셋** — 문서에 실제 쓰인 글자의 글리프만 남긴다. PyMuPDF는
`Document.subset_fonts()` 로 제공한다.

```
서브셋 적용        : 236 KB   (99.1% 감소)
garbage collect만  : 14.8 MB  (부족하다)
```

**순서가 중요하다.** 서브셋 뒤에 텍스트를 더 그리면(예: 쪽 번호) 그 글꼴이 다시
통째로 임베딩되어 237KB짜리가 7.6MB로 되돌아간다. 페이지에 얹을 것을 **먼저** 다
그리고 마지막에 서브셋해야 한다.

### DocumentWriter를 파일 경로에 직접 걸지 말 것

Windows에서 `DocumentWriter(str(path))` 로 쓰면 `close()` 후에도 핸들이 남아,
그 파일을 열어 후처리하고 교체하는 작업이 조용히 실패한다. 예외가 삼켜지면
"서브셋을 적용했는데 크기가 그대로"인 상태로 끝난다.

```python
buf = io.BytesIO()
writer = pymupdf.DocumentWriter(buf)   # 메모리 버퍼에 조판
...
pdf = pymupdf.open("pdf", buf.getvalue())  # 후처리 후 한 번만 저장
```

### Story는 표 열 너비의 백분율을 존중하지 않는다

`<td style="width:83%">` 로 지정한 열이 실제로는 **35%만** 차지했다. 그 결과 제목이
좁은 칸에 밀려 두 줄로 깨졌다. `table-layout: fixed` 도 소용없다.

**pt 절대값은 정확히 반영된다.** 원본의 열 너비 비율을 실제 본문 폭에 맞춰 pt로
환산해 넘기면 된다. 두 가지를 함께 조정해야 한다.

* `body { margin: 0 }` — 기본 여백이 표를 좌측으로 10.5pt 밀어낸다.
* 열당 오버헤드 **9pt** — padding(8pt) + 테두리 몫. 8pt로 잡으면 열 수와 무관하게
  1~3pt씩 본문 폭을 넘어 표 오른쪽이 잘린다.

### 표 배경이 다음 쪽에 유령처럼 복사된다

표가 쪽을 넘기면 Story가 **첫 쪽의 셀 배경을 이후 모든 쪽에 그대로 다시 그린다.**
x좌표·폭·색이 첫 쪽과 똑같고 높이만 6pt로 뭉개진 채라, 그 띠가 본문 글줄 위에
얹혀 **취소선처럼 보인다.**

```
1쪽:  y=34.7  h=33.7   <- 정상 (셀 높이만큼)
2쪽:  y=34.7  h= 6.0   <- 유령
3쪽:  y=34.7  h= 6.0   <- 유령  (마지막 쪽까지 반복)
```

HTML/CSS로는 못 피한다. 실측으로 확인한 것들:

* `display:block` 을 주면 유령은 줄지만 **셀이 표에서 이탈**해 문서 끝으로 밀린다.
* `<span>` 배경은 Story가 아예 그리지 않는다.
* colspan 유무와 무관하다(한때 관련 있어 보였지만 탐지 조건이 좁았을 뿐이다).

그래서 **조판 결과를 살펴보고 유령이 생겼을 때만 셀 배경을 빼고 다시 조판**한다.
한 쪽짜리 문서나 표가 쪽을 넘기지 않는 문서는 배경을 그대로 살린다. 조판을 두 번
하는 비용은 0.1초 남짓이라 감수할 만하다.

### 서식 적용 여부는 화이트리스트로 판정한다

한/글 문서에서 취소선 여부를 이렇게 판정했다가 **모든 글자에 취소선**이 그어졌다.

```python
strike = (el.get("shape") or "NONE").upper() != "NONE"   # 위험
```

어떤 저장본은 취소선 없음을 `shape="NONE"` 이 아니라 `shape="3D"` 로 적는다.
`"3D" != "NONE"` 이므로 문서 전체가 취소선으로 덮인다.

"NONE이 아니면 적용"은 **모르는 값 하나에 문서 전체가 망가지는** 판정이다. 알려진
값일 때만 켜는 화이트리스트가 안전하다.

```python
_STRIKE_ON = {"SOLID", "DASH", "DOT", "DASH_DOT", ...}
strike = (el.get("shape") or "").upper() in _STRIKE_ON
```

덧붙여 같은 `"3D"` 라도 **테두리에서는 유효한 선 종류**다. 같은 문자열이 문맥에
따라 다른 뜻을 갖는다는 점도 함정이다.

### 열 너비를 아예 주지 않으면 긴 값이 잘린다

조판 엔진이 내용에 맞춰 열을 배분하는데, **대부분의 행이 비어 있고 한 행에만 긴
값이 있는 열**은 극단적으로 좁아진다. 그 칸의 값이 넘쳐서 잘린다(낱말 중간에서는
줄바꿈이 안 되기 때문).

열 너비 정보가 없을 때는 내용으로 추정하되, 각 열의 **최장 낱말**을 최소 폭으로
보장해야 한다.

### PDF 읽기는 재구성이다

PDF에는 문단 개념이 없다. 글리프가 좌표에 찍혀 있을 뿐이다. 그래서 순서가 중요하다.

1. `find_tables()` 로 표 영역을 먼저 확정하고 그 사각형을 기억한다.
2. 텍스트 블록을 얻어, 표 영역과 겹치는 것은 건너뛴다(중복 방지).
3. 남은 블록을 y좌표로 정렬해 문단으로 만든다.
4. 본문 글자 크기의 **중앙값**을 기준으로, 뚜렷이 큰 문단을 제목으로 승격한다.

`find_tables()` 가 돌려주는 bbox는 버전에 따라 `Rect` 일 수도 튜플일 수도 있다.
한쪽만 가정하면 `AttributeError` 로 터진다.

CJK끼리 줄을 이을 때는 공백을 넣지 말아야 한다. 넣으면 어색하게 벌어진다.

## HWPX (한/글, OWPML)

ZIP + XML이라 사실상 한글판 OOXML이다. **한컴오피스 없이 읽고 쓸 수 있다.**

```
mimetype                    application/hwp+zip
version.xml                 HCFVersion
META-INF/container.xml      rootfile -> Contents/content.hpf
Contents/header.xml         참조 테이블(글꼴/글자모양/문단모양/테두리/스타일)
Contents/section0.xml       본문 (구역마다 파일 하나)
Contents/content.hpf        OPF 매니페스트 + 메타데이터
BinData/*                   임베디드 이미지
```

ODF와 달리 `mimetype` 을 무압축·첫 엔트리로 둘 필요가 없다(한/글 자신도 압축해 둔다).

### 본문은 서식을 참조만 한다

`section0.xml` 은 `charPrIDRef="5"` 처럼 **ID로 참조**할 뿐이다. 그래서 Writer는
2패스로 돈다 — 먼저 IR을 훑어 등장하는 서식 조합을 모아 ID를 매기고, 그 테이블로
`header.xml` 을 만든 뒤, 본문은 ID만 쓴다.

`charPr` 의 `fontRef` / `ratio` / `spacing` / `relSz` / `offset` 은 7개 언어 속성
(`hangul` `latin` `hanja` `japanese` `other` `symbol` `user`)을 **모두** 요구한다.
하나라도 빠지면 한/글이 파일을 거부한다.

### 셀 배경과 테두리는 borderFill 테이블에 있다

셀에는 `borderFillIDRef` 만 있고, 실제 배경색과 4방향 테두리는 `header.xml` 의
`borderFill` 항목에 있다. 이 테이블을 읽지 않으면 **음영과 테두리가 통째로 사라져**
변환 결과가 균일한 격자로 보인다. 한/글 양식 문서는 칸마다 테두리 유무가 다른
경우가 많아(제목 칸만 상자, 본문은 좌우선만) 차이가 크게 드러난다.

### paraPr의 여백·줄간격은 switch 안에 숨어 있다

```xml
<hh:paraPr id="16">
  <hp:switch>
    <hp:case hp:required-namespace="...">
      <hh:margin>...</hh:margin>
      <hh:lineSpacing type="PERCENT" value="160"/>
    </hp:case>
    <hp:default> ... 같은 내용 ... </hp:default>
  </hp:switch>
</hh:paraPr>
```

`paraPr/margin` 으로 찾으면 전부 놓친다. `default` 를 우선해 읽는 편이 안전하다.

### 표에서 병합된 칸은 `<tc>` 자체가 없다

행마다 셀 개수가 다르다(`colCnt=2` 인데 행별 셀 수가 `[2, 2, 1, 1, ...]`). 선언된
`rowCnt × colCnt` 격자를 만들고, 각 셀을 `cellAddr(colAddr, rowAddr)` 좌표에 놓은 뒤
`cellSpan` 이 덮는 칸을 자리표시자로 채워야 그리드가 맞는다.

### 단위가 두 가지다

* 길이: **HWPUNIT** = 1/7200인치 (1pt = 100)
* 글자 크기 `charPr/@height`: **1/100 pt** (1200 = 12pt)

같은 파일 안에서 섞여 있으니 혼동하지 말 것.

### 쪽 번호는 본문이 아니라 구역 컨트롤에 있다

`<hp:ctrl><hp:pageNum pos="BOTTOM_CENTER" sideChar="-"/></hp:ctrl>`. 본문만 훑으면
쪽 번호가 사라진다.

## HWP 5.0 (구형 바이너리)

OLE 복합 문서(CFB) 안에 압축된 바이너리 레코드 트리. **읽기는 되지만 쓰기는
현실적으로 불가능하다** — 한/글이 파일을 열 때 검사하는 내부 정합성 조건이 공개
명세에 다 나와 있지 않다.

### 압축은 raw deflate다

```python
zlib.decompress(raw, -15)   # wbits=-15. 평범한 decompress()는 실패한다.
```

### 레코드 헤더는 32비트에 세 필드를 욱여넣는다

```
tag_id = v & 0x3FF          (10비트)
level  = (v >> 10) & 0x3FF  (10비트)
size   = (v >> 20) & 0xFFF  (12비트)
```

`size` 가 12비트라 4095를 넘으면 `0xFFF` 표식을 두고 **다음 4바이트에 실제 크기**를
쓴다. 이 확장 규칙을 놓치면 스트림 전체가 어긋난다.

### 본문 텍스트의 제어 문자는 길이가 다르다

`PARA_TEXT` 는 UTF-16LE인데 제어 문자가 섞인다. 차지하는 길이가 다르다.

* 1 WCHAR: `0, 10, 13, 24~31`
* 8 WCHAR(16바이트): `1~9, 11~23`

잘못 건너뛰면 쓰레기 글자가 섞이거나 뒷부분이 통째로 밀린다. `11` 은 표/그리기
개체 자리이고, `9` 는 탭이다.

### 셀과 그 안의 문단이 같은 level이다

표 셀 내용을 `level > cell_level` 로 찾으면 안 된다. 실제 파일에서 셀의
`LIST_HEADER` 와 그 안의 `PARA_HEADER` 가 **같은 level** 로 나온다.

```
L2 LIST_HEADER      <- 셀 시작
L2 PARA_HEADER      <- 셀 내용 (같은 level!)
  L3 PARA_TEXT
```

같은 level도 받아들이고 **다음 `LIST_HEADER` 가 나오거나 표 밖으로 나갈 때**
멈춰야 한다. 이 조건을 틀리면 표가 통째로 빈 칸이 된다(실측: 7x4 표에서 12자만
남았다).

### 셀 헤더의 문단 수는 INT32다

`LIST_HEADER` 의 첫 필드를 INT16으로 읽으면 이후 필드가 2바이트씩 밀려 **col과
row가 뒤바뀐다.** 셀이 엉뚱한 자리에 놓이고 서로 덮어써서 값이 사라진다.

```
01000000  문단 수  (INT32)   <- 2바이트가 아니다
20000000  속성     (UINT32)
0100      col
0000      row
0100      colSpan
0100      rowSpan
```

### 그림 레코드 태그는 85다

`HWPTAG_BEGIN + 67`(=83)은 CURVE고, 그림은 **`HWPTAG_BEGIN + 69`(=85)** 다.
태그를 틀리면 그림을 하나도 못 찾는다.

BinData ID는 페이로드 **offset 71**에 있다. 앞부분 길이가 고정이라 바로 집을 수
있다 — 테두리 12 + 이미지 사각형 32 + 자르기 16 + 안쪽 여백 8 = 68, 그 뒤에
밝기·명암·효과 3바이트가 붙는다. 사각형(offset 12~43)에서 표시 크기도 얻는다.

### 서식 테이블 읽기 실패가 본문을 막으면 안 된다

`DocInfo` 는 글꼴·글자모양 테이블일 뿐이다. 여기서 예외가 나도 본문(`BodyText`)은
읽어야 한다. 기본 서식으로 진행하면 된다.

## DOCX

### `id(lxml 프록시)` 로 병합 셀을 판별하면 안 된다

python-docx의 `row.cells` 는 병합된 셀을 span 수만큼 반복해서 돌려준다. 중복을
걸러야 하는데 `id(tc._tc)` 를 쓰면 안 된다 — **lxml은 요소에 접근할 때마다 새
프록시를 만들고, 이전 프록시가 GC되면 같은 메모리 주소가 재사용된다.** 서로 다른
셀이 같은 id를 갖게 되어 멀쩡한 셀이 병합 자리로 오판된다.

실측: 12,061자짜리 표가 6,093자로 줄었다(절반 유실).

`<w:tr>` 의 `<w:tc>` 를 직접 순회하고 `gridSpan` / `vMerge` 를 읽으면 된다. 이때
`.//gridSpan` 으로 찾으면 **중첩 표 안쪽 셀의 값**까지 잡히므로 `tcPr/gridSpan` 으로
한정해야 한다.

### 병합과 내용 쓰기를 한 루프에서 섞지 말 것

`Table.cell(r, c)` 는 tc 요소를 훑어 격자를 매번 재계산한다. 중간에 병합이 일어나면
그 이후 행의 좌표 매핑이 어긋난다. 실측에서 3행까지만 채워지고 나머지 14행이 빈
셀로 남았다(11,889자 → 86자).

**내용을 전부 채운 뒤 병합**해야 한다.

### 한글 글꼴은 `w:eastAsia` 에 지정한다

`run.font.name = "맑은 고딕"` 은 `w:ascii` 와 `w:hAnsi` 만 설정한다. Word는 문자
계열별로 글꼴을 따로 고르고 **한글/한자/가나는 `w:eastAsia`** 를 본다. 이걸 빼면
한글만 엉뚱한 기본 글꼴(대개 굴림)로 렌더링된다.

### 문단과 표를 따로 읽으면 순서가 사라진다

`document.paragraphs` 와 `document.tables` 를 각각 읽으면 표가 전부 뒤로 밀린다.
`body` 의 XML 자식을 직접 순회해야 원래 순서가 보존된다.

## IR 설계

### 순회 함수는 중첩까지 일관되게 훑어야 한다

`tables()` 는 중첩 표를 재귀로 훑는데 `images()` 는 최상위만 보는 식으로 어긋나
있으면, 표 칸에 든 그림이 "이미지 0개"로 보고된다. 한/글 양식 문서는 도장·서명을
표 칸에 넣는 경우가 흔해서 바로 드러난다.

통계도 마찬가지다. 최상위만 세면 **문서 전체가 표 한 장인 양식 문서**가
"문단 0개, 글자 0개"로 나와 변환이 실패한 것처럼 보인다.

## 인코딩

### CSV는 UTF-8 BOM으로 내보낸다

Excel은 BOM 없는 UTF-8 CSV를 시스템 코드페이지(한국어 Windows는 CP949)로 해석해
한글을 깨뜨린다. `utf-8-sig` 로 저장하면 Excel도 메모장도 올바로 연다.

### 읽을 때는 점수제로 판별한다

CP949 저장본과 UTF-8이 섞여 돌아다닌다. `latin-1` 은 **어떤 바이트열이든 디코딩에
성공**하므로 "성공 여부"만으로는 판별이 안 된다. 디코딩 결과에서 한글/ASCII 비율과
치환문자(`�`)·제어문자 비율을 점수화하고, 엄격한 인코딩에 가산점을 준다.

### `wdFormatUnicodeText = 7` 은 평문이 아니다

Word COM의 `WdSaveFormat` 상수는 이름만 보고 넘겨짚으면 틀린다.

```
wdFormatText        = 2     ← 평문
wdFormatDOSText     = 4
wdFormatUnicodeText = 7     ← UTF-16!
```

7을 평문 txt로 쓰면 결과가 UTF-16LE로 저장되어 UTF-8로 읽는 쪽에서 전부 깨진다
(실측: 깨진 문자 10,694개). `Encoding` 인자로 UTF-8을 요청해도 버전과 로캘에 따라
무시되므로, **저장 후 인코딩을 확인해 UTF-8로 정규화**하는 편이 확실하다.

## 변환 경로

### 2단계 경유로는 메워지지 않는 칸이 있다

`doc → xls` 는 어떤 2단계 조합으로도 불가능하다.

* `doc→docx` 는 되지만 `docx→xls` 가 안 된다 (Excel은 docx를 못 읽는다)
* `csv→xls` 는 되지만 `doc→csv` 가 안 된다 (Word는 csv를 못 만든다)

실제로 필요한 경로는 3단계다.

```
doc →[Word]→ docx →[native]→ xlsx →[Excel]→ xls
```

경로 탐색을 **너비 우선**으로 일반화하면 이런 칸이 자동으로 메워진다. 너비 우선이면
항상 가장 짧은 길을 고르는데, 경유가 늘수록 서식 손실이 쌓이므로 이 성질이 중요하다.

### LibreOffice headless 주의점

* 같은 사용자 프로필을 두 프로세스가 동시에 쓰지 못한다. 사용자가 LibreOffice를
  켜 둔 상태면 실패하거나 GUI가 뜬다. 변환마다 임시 프로필을 지정한다
  (`-env:UserInstallation=file:///...`).
* 출력 파일 이름을 지정할 수 없다. `--outdir` 에 원본 이름 + 새 확장자로 떨어지므로
  임시 디렉터리에 만든 뒤 옮긴다.

## 텍스트 추출

### CJK와 라틴 사이에 공백이 끼어든다

Word가 만든 PDF에서 `1,234,567원` 이 `1,234,567 원` 으로 추출됐다. 한글과 라틴·숫자
사이에 **자동 자간**이 들어가면서 별도 조각으로 분리되고, 텍스트 추출 시 그 틈이
공백이 되기 때문이다. 내용이 없어진 게 아니다.

검증용 표본 문자열은 이 경계를 걸치지 않게 골라야 한다. 그렇지 않으면 멀쩡한
변환이 실패로 잡힌다.

## 시험 설계

특정 개인의 파일에 기대면 저장소를 내려받은 사람이 시험을 돌릴 수 없다. 검증에
필요한 표본은 **프로그램 자신이 만들어 쓰는** 편이 낫다(`tests/sample.py`). 제목,
서식, 표, 병합, 배경, 테두리를 고루 담은 문서를 IR로 조립해 내보내면 된다.

`.hwp` 처럼 쓰기를 지원하지 않는 형식은 명세대로 조립한 합성 표본을 쓴다
(`tests/make_hwp_sample.py`). 레코드 순회·압축 해제·텍스트 디코딩은 이것으로
검증되지만, 실제 한/글이 저장한 파일의 다양한 컨트롤까지 확인해 주지는 못한다.
이 한계는 명시해 두는 게 정직하다.
